# HPS 编号脚本代码风格规范（中文初学者版）

这份文档用来总结当前 `high-precision-segmentation` 工程里 01～17 编号脚本的写法。

目标不是写“最短代码”，而是写“我能一行一行读懂、现场能放心运行、以后还能继续改”的代码。


## 1. 总体风格

每个编号脚本都尽量是一个独立可运行的小流程：

```bash
python scripts/XX_name.py
```

脚本自己说明它做什么、需要什么输入、会不会保存文件、会不会连接相机或机械臂。

现在推荐的风格是：

- 一个脚本解决一个明确任务。
- 能不依赖 `src/hps` 就不依赖。
- 能不读额外 yaml 配置就不读。
- 现场确认过的参数直接放在脚本顶部。
- 不为了“通用”写很多未来可能用不到的分支。
- `main()` 像一张流程清单，从上往下能看懂整件事。


## 2. 当前主线脚本

当前工程主线更接近下面这条顺序：

```text
01 检查环境
03 采集 RealSense RGBD
04/05 转换标注数据
06 训练 YOLO 分割模型
07 实时预览分割效果
15 黄色试管单根抓取放置 Demo
17 黄色 + 紫色两根试管连续抓取放置 Demo
```

旧的实验脚本、学习文档和过渡版本可以放进归档目录，不要混在当前主线里误导自己。


## 3. 文件结构顺序

推荐每个脚本按这个顺序写：

```python
#!/usr/bin/env python3
"""中文说明：这个脚本做什么、流程是什么、哪些模式会真实运行。"""

from __future__ import annotations

# 1. import
# 2. 固定参数
# 3. 小数学函数 / 小工具函数
# 4. 文件、相机、模型读取
# 5. 图像几何计算
# 6. 机械臂小包装
# 7. 路径规划
# 8. 真正执行动作
# 9. 命令行参数和 main()
```

小脚本不必强行凑齐所有部分。真实用不到的部分就不要写。


## 4. 顶部 docstring 应该写什么

脚本最上面的三引号说明要让人一打开就知道：

- 这是第几步脚本。
- 输入是什么，例如相机、图片、模型、标定文件。
- 输出是什么，例如预览窗口、训练结果、机器人动作。
- 默认模式会不会动硬件。
- `--check-ik` 和 `--execute` 的区别。
- 建议从 `main()` 开始读。

示例风格：

```python
"""脚本17：先抓黄色试管到凹槽，再抓紫色试管到凹槽。

流程：
1. RealSense + YOLO 同时找到黄色和紫色试管；
2. 按 C 锁定稳定目标；
3. 先执行黄色试管完整抓取放置；
4. 回到零位后，再执行紫色试管完整抓取放置。
5. POS/NEG 分支和 yaw 候选绑定，避免固定关节表不配套。

默认只做视觉预览。--check-ik 只读检查路径，--execute 才真实运动。
"""
```


## 5. 固定参数写在脚本前面

现场确认过的参数放在脚本顶部，名字要直接说明含义和单位。

推荐命名：

- `_PX`：像素
- `_MM`：毫米
- `_M`：米
- `_DEG`：角度
- `_RAD`：弧度
- `_SECONDS`：秒
- `_JOINTS`：六关节角

示例：

```python
TABLE_Z_ARM_MM = 68.12483333
GRASP_Z_M = 0.165
APPROACH_Z_M = 0.350
WAIT_SECONDS = 1.5
```

机械臂固定点建议用二维数组保存，尤其是同一类动作有固定顺序时。

例如黄色试管正角度分支：

```python
# 第0行：盖子朝上；第1行：凹槽上方；第2行：凹槽释放；第3行：松爪后撤回。
YELLOW_TUBE_POS_JOINTS = np.array(
    [
        [...],
        [...],
        [...],
        [...],
    ],
    dtype=np.float64,
)
```

这样比 `joint_1`、`joint_2`、`joint_3` 更不容易忘记每个关节位的用途。


## 6. 配置文件原则

当前工程倾向于少配置、少绕路：

- 简单固定值直接写在脚本顶部。
- `configs/classes.txt` 可以保留，因为类别名称属于数据集约定。
- 不再为了几个固定参数额外维护 `vision.yaml`。
- 不再把主要流程藏到 `src/hps` 下面。

如果一个配置只有一个脚本使用，而且经常需要结合代码理解，那就优先直接写进脚本。


## 7. 函数设计原则

一个函数只做一件有意义的事。

推荐：

- `load_calibration()`：读取标定。
- `pixel_to_arm()`：像素点转机械臂基座坐标。
- `detect_and_lock()`：相机实时检测并按 C 锁定。
- `build_one_tube_plan()`：为一根试管准备抓取和放置计划。
- `execute_one_tube_plan()`：真正按顺序运动机械臂。

不推荐：

- 为了“看起来高级”写很多层包装。
- 一个函数里面同时读相机、算几何、连机械臂、执行动作。
- 很多只调用一次、没有解释价值的一行小函数。
- 很多兼容未来设备的抽象类。


## 8. `main()` 的风格

`main()` 应该像现场操作清单。

推荐感觉：

```python
def main() -> int:
    args = parse_args()

    calibration = load_calibration()
    solution = detect_and_lock(args, calibration)

    if not (args.check_ik or args.execute):
        print("[PREVIEW ONLY] 没有连接机械臂。")
        return 0

    robot = SimpleCArm(args.ip)
    try:
        check_start_from_zero(robot)
        plan = build_plan(robot, solution)

        if args.execute:
            execute_plan(robot, plan)
        else:
            print("[IK CHECK ONLY] 没有使能、没有运动。")
    finally:
        robot.close()

    return 0
```

读 `main()` 时，应该能看出：

- 先读参数；
- 再读标定；
- 再视觉锁定；
- 再决定是否连接机械臂；
- 再检查 / 执行；
- 最后关闭连接。


## 9. 注释风格

注释要解释“为什么”和“物理意义”，不要只是翻译语法。

推荐解释：

- 这个坐标是像素、毫米还是米。
- 这个 yaw 是图像角度还是机械臂基座角度。
- 这个关节表第 0/1/2/3 行分别是什么。
- 这个确认文字是为了防止误触发真实运动。
- 这个高度是为了减少碰撞风险。
- `--check-ik` 只是只读检查，不代表真实运动一定没有碰撞。

不推荐解释：

```python
x += 1  # x 加 1
print(x)  # 打印 x
```

对初学者真正有用的是：

```python
# 图像坐标 y 轴向下，所以图像角度只用于判断试管在画面里的正负方向；
# 机械臂真正抓取使用的是转换到基座坐标后的 tube_yaw。
```


## 10. 视觉脚本风格

视觉相关脚本要把下面几件事写清楚：

- 使用哪个模型权重。
- 模型类别顺序是什么。
- 相机序列号和分辨率是什么。
- 是否使用 RealSense。
- 是否只预览，不保存、不控制机械臂。
- 画面上显示哪些信息。

当前试管分割类别顺序固定为：

```python
MODEL_CLASSES = ("p-body", "p-cap", "y-body", "y-cap")
```

脚本 17 这种 Demo 里，实时画面左上角应该尽量显示关键信息：

```text
STABLE — C-lock
YELLOW IMAGE B→C: 72.3 deg
BASE YAW Y: 16.1 deg

PURPLE IMAGE B→C: 106.2 deg
BASE YAW P: -18.0 deg
```

这样现场调试时不用去猜当前锁定的是哪根试管、哪个角度。


## 11. 机械臂脚本风格

机械臂脚本必须把三种模式分清楚：

```text
默认运行：只视觉预览，不连接机械臂。
--check-ik：连接机械臂，只读检查当前状态和 IK，不使能、不运动。
--execute：确认后真实执行动作。
```

真实执行前要有确认文字。

示例：

```text
请输入完整确认文字：
GRASP_CAP_UP 黄色试管 tool=1 x=... y=... z=...
```

这不是为了麻烦，而是为了避免终端误触发机械臂运动。


## 12. 固定关节流程的风格

当前 15/17 的 Demo 更适合“固定现场关节表”：

- 图像角度为正：用 POS 关节表。
- 图像角度为负：用 NEG 关节表。
- 第 0 行：盖子朝上。
- 第 1 行：凹槽上方。
- 第 2 行：凹槽释放。
- 第 3 行：松爪后撤回。
- 最后回到六关节零位。

这样比在凹槽处继续用 XYZ + 四元数反复求 IK 更简单、更稳定，也更符合现场调试习惯。

注意：固定关节表只适合已经实测过的凹槽和机械臂安装环境。如果夹爪、工具坐标、凹槽位置或工作台改变，必须重新标定这些关节位。


## 13. 路径搜索不要过度复杂

可以保留确实能提高成功率的搜索，例如：

- 两个等价抓取 yaw。
- 必要的 twist 候选。
- 先 `--check-ik` 再 `--execute`。

但不要写太多极少数情况的兜底：

- 不要为了未来可能多个相机写复杂设备工厂。
- 不要为了未来可能多个机器人写通用机器人接口。
- 不要为了一个固定点写一堆候选点循环。
- 不要让失败汇总比主流程还难读。

原则是：现场真的用过、真的能提高成功率，就保留；只是想象中的“更通用”，先不要写。


## 14. 错误提示风格

错误提示要直接告诉人哪里错了。

推荐：

```python
raise ValueError(f"实时内参与标定不一致：{error:.3f} px")
raise RuntimeError("机械臂必须从六关节零位开始")
raise RuntimeError("IK 没有返回关节解")
```

不要写太抽象的：

```python
raise RuntimeError("failed")
```


## 15. 命令行风格

命令行参数用 `argparse`，默认值写清楚。

常见参数：

```python
parser.add_argument("--model", help="YOLO Seg 权重；默认最新 best.pt")
parser.add_argument("--serial", help="可选 RealSense 序列号")
parser.add_argument("--ip", default=DEFAULT_IP)
parser.add_argument("--check-ik", action="store_true", help="只检查 IK，不运动")
parser.add_argument("--execute", action="store_true", help="确认后真实执行")
```

如果某个参数不再生效，就删除它，不要留在命令行里误导自己。

例如已经固定用 FP32，就不要继续保留没效果的 `--half`。


## 16. 验证方式

每次改代码后，至少做两类检查：

```bash
conda run -n hps python -m py_compile scripts/*.py scripts_archive/*.py
python scripts/17_demo_two_tube_branch_yaw.py --help
```

如果涉及相机或机械臂，还要分清楚：

- `py_compile` 只能说明语法没错。
- `--help` 只能说明命令行能解析。
- `--check-ik` 只说明连接和只读规划通过。
- `--execute` 才是真实运动验证。

不要把 “IK 通过” 说成 “真实运动一定安全”。


## 17. 不要做的事

以后重写或新写编号脚本时，尽量避免：

- 导入另一个编号脚本。
- 大量使用 `src/hps` 隐藏主流程。
- 留下已经不用的 yaml 配置。
- 留下已经不用的函数、常量和命令行参数。
- 用复杂抽象替代现场固定参数。
- 为了代码短而删除真实执行前的确认。
- 把没有实测过的机械臂动作说成已经验证。
- 在注释里写和代码不一致的话。


## 18. 修改代码时的判断原则

这几条是以后让 Codex 或自己修改本工程脚本时的优先级。它们比“代码越短越好”更准确：

```text
只改必要的地方，让核心功能先完成；
不为一次性逻辑造大框架；
不猜未来需求；
真实边界要检查，内部确定的数据不要重复防御；
错误要暴露，不要被静默兜底藏起来。
```

### 最小改动原则

只修改完成当前任务必须修改的代码。

如果用户只要求改脚本 17 的某一步动作，就不要顺手重构视觉检测、训练脚本或历史归档脚本。除非这些地方确实阻塞当前任务，否则保持不动。

### 反过度工程

能直接解决就直接解决。

不要为了一个固定现场流程，额外创建复杂的类、工具层、抽象层、配置系统或框架。比如当前 15/17 的固定关节表已经足够清楚时，就不要再为它写一套“通用机器人任务引擎”。

### 反推测性开发

不要实现用户没有要求的“以后可能会用到”的功能。

低概率场景可以先记录，但不要为了它们堆大量 edge case。真正发生时，再根据现场证据修改。

### 合理防御，而不是取消防御

简单不等于不要检查。

下面这些是真实系统边界，应该保留检查：

- 用户输入的路径、类别、命令行参数；
- 文件覆盖和数据集转换；
- 模型类别顺序；
- 相机连接和实时内参；
- 机械臂连接、起始零位、IK 检查和真实执行确认；
- GitHub、网络、外部 API、硬件 SDK 返回值。

但程序内部已经有明确保证的数据，不要层层重复验证。重复检查如果不能提供新的安全性，只会让代码难读。

### 错误应该暴露

不要用宽泛的 `except Exception`、静默默认值、无意义 fallback 把真正的问题藏起来。

如果 IK 没有解，就直接说 IK 没有解；如果模型类别不对，就直接报类别不对。无法继续时快速失败，并明确说明原因。

### 不要假装确定

遇到接口含义、坐标系、单位、数据格式、四元数顺序、机械臂关节姿态等不确定的地方，不要把猜测写成事实。

可以提出最小可验证假设，但必须说清楚：

- 哪里不确定；
- 当前为什么这样猜；
- 需要什么信息或实测结果才能确认。

### 先定义成功标准再修改

修改前先想清楚“什么叫修好了”。

例如：

- 环境脚本：`python scripts/01_check_environment.py --with-yolo` 通过；
- 视觉脚本：窗口能显示目标、B/C 点和角度；
- 机器人脚本：`--check-ik` 通过只是只读检查，`--execute` 跑完才是真机验证；
- GitHub 上传：网页仓库能看到 README 和文件，而不是本地 commit 完就算完成。

代码写完不等于任务完成。要用对应的运行、检查或用户确认来闭环。

### 优先核心功能

不要出现“为了一个功能造了一座堡垒，最后核心功能反而没完成”的情况。

本工程的核心功能是：

```text
采集数据 -> 训练/预览分割 -> 检测试管 -> 抓取 -> 放置 -> 回零
```

所有代码结构、注释、检查和文档都应该服务这条主线。


## 19. 最终一句话

这个工程的编号脚本风格是：

```text
一个脚本，一个任务；参数在前，流程在后；
注释讲物理意义和为什么；
默认不动硬件，执行必须确认；
最小改动、少抽象、少兜底、少配置；
优先让初学者和现场调试都能看懂，同时保留真实系统边界的必要检查。
```
